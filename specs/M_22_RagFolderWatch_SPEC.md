# M_22 RagFolderWatch — RAG 폴더 감시 자동 인제스트 + UI 폴더 동기화

CR-41. 서버의 `RAG/` 디렉토리를 감시해, 파일을 넣으면 자동으로 임베딩하고
디렉토리 구조를 앱의 문서 폴더와 맞춘다.

## 문제

지금 문서를 넣는 경로가 셋이고 전부 수동이다.

1. 브라우저 업로드 — 파일이 터널을 왕복해 수백 개는 터널이 먼저 끊긴다
2. `scripts/bulk_ingest.py` — 서버에 올린 뒤 사람이 명령을 실행해야 한다
3. 앱의 폴더 구조는 `data/rag_originals/<folder_id>/`라는 **불투명한 ID 디렉토리**여서
   파일 탐색기로 열어봐도 뭐가 뭔지 알 수 없다

## 설계

```
RAG/                      ← 감시 루트 (설정: app.rag_watch.root)
├── 완결보고서/            ← 서브디렉토리 이름 = 앱 문서 폴더 이름
│   └── TRKO...pdf        ← 넣으면 자동 인제스트
└── RFP/
    └── 공고문.pdf
```

- `RAG/` **직하 파일**은 폴더 없음(`__no_folder__`)으로 인제스트한다.
- 서브디렉토리 이름이 앱 폴더 이름이 된다. 2단 이상 깊이는 가장 위 서브디렉토리를
  폴더로 보고 그 아래는 평탄화한다(앱 폴더 모델이 1단이므로).

### 폴링을 쓰는 이유

inotify(watchdog)를 쓰지 않는다. 이 시스템은 **Lustre 병렬 파일시스템** 위에 있고,
Lustre는 다른 클라이언트에서 발생한 변경에 대해 inotify 이벤트를 전달하지 않는다.
MobaXterm SFTP 업로드가 다른 경로로 들어올 수 있으므로 이벤트 기반은 신뢰할 수 없다.
주기 스캔(기본 30초)은 느리지만 확실하고, 의존성도 늘지 않는다.

### 상태 파일

`data/rag_watch_state.json`

```json
{
  "files": {
    "<sha256(내용)>": {
      "path": "완결보고서/TRKO....pdf",
      "doc_id": "TRKO....pdf_a1b2c3d4",
      "folder_name": "완결보고서",
      "size": 5242880,
      "ingested_at": "2026-07-30T01:23:45+09:00"
    }
  }
}
```

**키가 경로가 아니라 내용 해시**인 이유: 파일을 다른 폴더로 옮기거나 이름을 바꿨을 때
같은 문서를 다시 임베딩하지 않기 위해서다. 해시가 이미 있으면
- 같은 폴더 → 건너뜀
- 다른 폴더 → `PATCH /documents/{doc_id}`와 동일한 이동 처리(청크 category 갱신)

크기·mtime만 보면 SFTP 업로드 중인 파일(부분 전송)을 완성본으로 착각한다. 그래서
**연속 두 번의 스캔에서 크기와 mtime이 동일할 때만** 인제스트한다(안정화 확인).

## 삭제 정책 — 기본은 "무시"

`app.rag_watch.delete_policy` (기본 `ignore`)

| 값 | 동작 |
|----|------|
| `ignore` (기본) | 파일이 사라져도 임베딩을 남긴다. 로그만 남김 |
| `unindex` | 파일이 사라지면 해당 문서를 색인에서 제거 |

기본을 `ignore`로 두는 이유: 파일시스템 사고(마운트 실패, 실수한 이동, SFTP 중단)로
**문서 수백 건이 조용히 사라지는 것**이 잘못 남아 있는 것보다 훨씬 위험하다.
색인 정리는 UI에서 명시적으로 하는 것이 안전하다.

## 폴더 양방향 동기화

매 스캔마다 `rag_folders.json`과 `RAG/` 서브디렉토리 목록을 맞춘다.

| 상황 | 처리 |
|------|------|
| `RAG/`에만 있는 디렉토리 | 앱 폴더 생성 |
| 앱에만 있는 폴더 | `RAG/<이름>/` 디렉토리 생성 (UI에서 만든 폴더가 파일탐색기에도 보이게) |
| UI에서 폴더 이름 변경 | 다음 스캔에서 새 이름 디렉토리가 생긴다. **기존 디렉토리는 지우지 않는다** — 안에 파일이 있을 수 있으므로 사람이 판단한다(로그로 안내) |
| 앱 폴더 삭제 | `RAG/` 디렉토리는 그대로 둔다(삭제 정책과 같은 이유) |

폴더 이름은 파일시스템 안전 문자로 제한한다(`/`, `\`, 널 문자, 선행·후행 공백 제거).

## 설정 (`conf.yaml` → `app.rag_watch`)

| 키 | 기본값 | 의미 |
|----|--------|------|
| `enabled` | `false` | 감시 사용 여부 |
| `root` | `""` | 감시 디렉토리 절대경로. 비우면 비활성 |
| `interval_seconds` | `30` | 스캔 주기 |
| `delete_policy` | `ignore` | `ignore` \| `unindex` |
| `max_per_cycle` | `20` | 한 주기에 처리할 최대 파일 수. 수백 개가 한꺼번에 들어와도 채팅·TTS가 굶지 않게 나눠 처리한다 |
| `unindex_guard_ratio` | `0.25` | 한 주기 삭제가 추적 문서의 이 비율을 넘으면 삭제 중단 |
| `unindex_guard_min` | `5` | 이 개수 이하는 비율 가드를 통과 |

## 인제스트 경로 공유

`rag_routes.upload_document`의 파싱·청킹·임베딩·원본저장을
`ingest_document_bytes(ctx, filename, data, folder_id)`로 추출하고 라우트는 얇은 래퍼가 된다.
감시자는 같은 함수를 호출한다 — **인제스트 로직을 두 벌 유지하지 않는다**(청킹 파라미터가
갈라지면 브라우저 업로드와 자동 인제스트의 결과가 달라진다).

## 자동 시딩

이미 인제스트된 파일이 감시 폴더에 있으면 감시자는 신규로 보고 **전부 중복 임베딩한다.**
270건이면 색인이 두 배로 불고 검색에 중복이 뜬다.

그래서 **백엔드가 첫 스캔 전에 자동으로 시딩한다** (`RagWatchService.seed_from_existing`).
벡터 스토어의 문서 목록을 읽어 `RAG/` 안의 파일 중 **(파일명, 폴더명)이 일치하는 것**을
"이미 인제스트됨"으로 기록한다. 사람이 스크립트를 돌리는 방식이었다면 "감시를 켰는데
시딩을 잊는" 사고가 남으므로 앱이 책임진다.

상태 파일에 기록이 하나라도 있으면 건너뛴다 — 재시작마다 반복할 필요가 없다.
시딩이 실패해도 감시는 계속하되, 중복 위험을 ERROR 레벨로 크게 남긴다.

## 대량 삭제 가드 (`delete_policy: unindex`일 때)

"파일이 없다"와 "폴더를 읽을 수 없다"를 구분할 방법이 없다. 마운트 실패·권한 오류로
`RAG/`가 비어 보이면 색인 전체가 삭제된다.

그래서 한 주기에 사라진 파일이 추적 문서의 `unindex_guard_ratio`(기본 25%)를 넘으면
**삭제를 중단하고 ERROR 로그만 남긴다.** 문서가 몇 건뿐일 때 비율 가드가 정상 삭제까지
막지 않도록 `unindex_guard_min`(기본 5) 이하는 비율과 무관하게 통과시킨다.

## 테스트 (`tests/rag_watch/`)

1. 새 파일 감지 → 인제스트 1회
2. 같은 파일 재스캔 → 재인제스트 안 함
3. mtime/크기가 변하는 중(전송 중) → 인제스트 보류, 안정화 후 실행
4. 내용 동일 파일을 다른 폴더로 이동 → 재임베딩 없이 폴더만 이동
5. 서브디렉토리 신규 → 앱 폴더 생성
6. 앱 폴더만 존재 → `RAG/` 디렉토리 생성
7. 파일 삭제 + `delete_policy=ignore` → 색인 유지
8. 파일 삭제 + `delete_policy=unindex` → 색인 제거
9. `max_per_cycle` 초과 → 초과분은 다음 주기로
10. 허용되지 않은 확장자 → 무시
11. 폴더명 새니타이즈(`../` 탈출 시도, 슬래시 포함)
12. 루트 미설정/미존재 → 조용히 비활성
